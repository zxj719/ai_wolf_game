一、先把 IMU 链路做出来

先写出来跑通，再回头讲每一处为什么这么写。

1.1 给 math_lib 加一个函数

Day 2 已经建立了「纯逻辑放 library」的习惯。模长计算与 ROS2 无关，照例放这里。 在 my_robot/math_lib.py 顶部加上 import math，末尾追加：

def magnitude(x: float, y: float, z: float) -> float:
    """三维向量的模长。IMU 的线加速度、角速度都用得上。"""
    return math.sqrt(x * x + y * y + z * z)

1.2 发布端 my_robot/imu_talker.py

新建这个文件。真实 IMU 驱动做的事和它一样：读硬件、填消息、发布； 这里用算出来的数代替硬件读数，其余部分没有区别。

import math

import rclpy
from rclpy.node import Node
from rclpy.qos import HistoryPolicy, QoSProfile, ReliabilityPolicy
from sensor_msgs.msg import Imu

from my_robot.math_lib import period_of

GRAVITY = 9.81


class ImuTalker(Node):
    def __init__(self):
        super().__init__('imu_talker')

        self.declare_parameter('imu_hz', 50.0)
        self.declare_parameter('frame_id', 'imu_link')
        hz = self.get_parameter('imu_hz').value
        self.frame_id = self.get_parameter('frame_id').value

        # 这段 QoS 先照抄，第四节专门讲它
        qos = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,
            history=HistoryPolicy.KEEP_LAST,
            depth=10,
        )
        self.pub = self.create_publisher(Imu, 'imu/data', qos)

        self.dt = period_of(hz)
        self.elapsed = 0.0
        self.timer = self.create_timer(self.dt, self.on_timer)
        self.get_logger().info(
            f'imu_talker 已启动：{hz} Hz，frame_id={self.frame_id}')

    def on_timer(self):
        self.elapsed += self.dt
        msg = Imu()

        # header 是所有传感器消息的共同前缀：这条数据什么时候、在哪个坐标系测的
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.header.frame_id = self.frame_id

        # 静止平放时加速度计测到的是重力反作用力：z 轴约 +9.81
        # 叠一个慢速正弦模拟轻微晃动
        wobble = 0.5 * math.sin(self.elapsed)
        msg.linear_acceleration.x = wobble
        msg.linear_acceleration.y = 0.0
        msg.linear_acceleration.z = GRAVITY

        msg.angular_velocity.x = 0.0
        msg.angular_velocity.y = 0.0
        msg.angular_velocity.z = 0.2 * math.cos(self.elapsed)

        # 本节点不估计姿态。按 Imu 消息的约定，
        # 协方差矩阵第 0 个元素填 -1 表示「这一项没有数据」
        msg.orientation_covariance[0] = -1.0

        self.pub.publish(msg)


def main():
    rclpy.init()
    node = ImuTalker()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

period_of 是 Day 2 写进 math_lib 的，这里直接复用——同一个包里的东西越用越顺手， 这正是把逻辑抽出来的回报。

1.3 订阅端 my_robot/imu_listener.py

Day 1 的 listener 只订阅不发布。从这个节点开始，节点处在数据链路的中间： 订阅一个话题，加工，再发布另一个话题。这是实际项目里最常见的形态。

import rclpy
from rclpy.node import Node
from rclpy.qos import HistoryPolicy, QoSProfile, ReliabilityPolicy
from sensor_msgs.msg import Imu
from std_msgs.msg import Float64

from my_robot.math_lib import magnitude


class ImuListener(Node):
    def __init__(self):
        super().__init__('imu_listener')

        # 订阅端的 QoS 必须与发布端兼容。这里和 imu_talker 用同一套配置
        qos = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,
            history=HistoryPolicy.KEEP_LAST,
            depth=10,
        )
        self.sub = self.create_subscription(Imu, 'imu/data', self.on_imu, qos)

        # 输出是一个普通的数，用默认 QoS（可靠传输）即可
        self.pub = self.create_publisher(Float64, 'imu/magnitude', 10)

        self.count = 0
        self.get_logger().info('imu_listener 已启动，正在订阅 imu/data')

    def on_imu(self, msg: Imu):
        a = msg.linear_acceleration
        out = Float64()
        out.data = magnitude(a.x, a.y, a.z)
        self.pub.publish(out)

        # 50 Hz 全打日志会刷屏，每 50 条打一次
        self.count += 1
        if self.count % 50 == 0:
            self.get_logger().info(
                f'已处理 {self.count} 条，最新模长 {out.data:.3f} m/s^2'
                f'（frame_id={msg.header.frame_id}）')


def main():
    rclpy.init()
    node = ImuListener()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

话题名照旧写相对名 imu/data，不带开头的 /。 Day 2 讲过：带 / 的绝对名不吃 namespace，launch 里给的 robot1 会失效。

二、消息结构：Imu 比 Int32 复杂在哪

Int32 只有一个 data 字段。传感器消息不一样。另开一个终端（记得先 cd ~/ros2_lab && source install/setup.bash）：

ros2 interface show sensor_msgs/msg/Imu

去掉开头的大段注释，结构是这样：

std_msgs/Header header
	builtin_interfaces/Time stamp
		int32 sec
		uint32 nanosec
	string frame_id

geometry_msgs/Quaternion orientation
	float64 x 0
	float64 y 0
	float64 z 0
	float64 w 1
float64[9] orientation_covariance # Row major about x, y, z axes

geometry_msgs/Vector3 angular_velocity
	float64 x
	float64 y
	float64 z
float64[9] angular_velocity_covariance # Row major about x, y, z axes

geometry_msgs/Vector3 linear_acceleration
	float64 x
	float64 y
	float64 z
float64[9] linear_acceleration_covariance # Row major x, y z

三件事值得注意。

第一，消息是可以嵌套的。 Imu 里装着 Header、Quaternion、三个 Vector3， 而 Header 里又装着 Time。缩进就是嵌套层级。所以代码里写 msg.linear_acceleration.x——先取字段，再取字段。

第二，float64[9] 是定长数组。 协方差矩阵是 3×3 按行铺平的 9 个数。 代码里 msg.orientation_covariance[0] = -1.0 就是在改第一个元素。

第三，注释是消息定义的一部分。 上面被我省掉的注释里写着一条约定：

如果你没有某一项的估计值（比如你的 IMU 不输出姿态）， 把对应协方差矩阵的第 0 个元素设成 -1。

这就是 imu_talker 里那行 orientation_covariance[0] = -1.0 的来历—— 它不是随便填的，是在按消息约定声明「姿态这一项我没有数据，别用」。 读别人的传感器数据时也要检查这个 -1。

2.1 Header：每条传感器数据都要回答的两个问题

ros2 interface show std_msgs/msg/Header
# Two-integer timestamp that is expressed as seconds and nanoseconds.
builtin_interfaces/Time stamp
	int32 sec
	uint32 nanosec

# Transform frame with which this data is associated.
string frame_id

只有两个字段，但它们回答了传感器数据最关键的两个问题：

字段回答什么不填会怎样
stamp这条数据是什么时候测的多个传感器的数据没法对齐；rviz2 会认为数据过期而不显示
frame_id这条数据在哪个坐标系里测的系统不知道雷达装在车的哪个位置，点云无法与底盘对上

stamp 必须用 ROS2 的时钟取，不要用 Python 的 time.time()：

msg.header.stamp = self.get_clock().now().to_msg()

frame_id 是一个坐标系的名字。Day 4 会把这些名字连成一棵 TF 树， 到时候 imu_link 这个名字就会和小车模型上的具体位置对应起来。今天先记住： 传感器数据必须声明自己属于哪个坐标系。

补充：快速看一条消息的骨架

interface show 给的是定义。想直接看一条「空消息」长什么样，用 proto：

ros2 interface proto sensor_msgs/msg/Imu

（节选）

"header:
  stamp:
    sec: 0
    nanosec: 0
  frame_id: ''
orientation:
  x: 0.0
  y: 0.0
  z: 0.0
  w: 1.0
orientation_covariance:
- 0.0
...

这个格式可以直接拿去填 ros2 topic pub 的参数（见第三节）。

想知道系统里有哪些传感器消息类型：

ros2 interface list | grep sensor_msgs

本机共 27 种，常见的有 Imu、LaserScan、PointCloud2、Image、JointState、 BatteryState。Day 4 会用到 LaserScan。

三、把运行中的系统看清楚

Day 1 用过 ros2 topic list 和 echo。今天把这套工具补全—— 它们是排查机器人问题的第一道手段，后面每天都要用。

3.1 有哪些话题，各是什么类型

ros2 topic list -t
/parameter_events [rcl_interfaces/msg/ParameterEvent]
/robot1/counter [std_msgs/msg/Int32]
/robot1/counter_doubled [std_msgs/msg/Int32]
/robot1/imu/data [sensor_msgs/msg/Imu]
/robot1/imu/magnitude [std_msgs/msg/Float64]
/rosout [rcl_interfaces/msg/Log]

-t 是 --show-types，把类型一起列出来。四个业务话题都带着 /robot1 前缀—— 这是 launch 里 namespace='robot1' 加上的。

刚启动时列表可能不全。DDS 的发现是渐进的，节点之间要花几秒互相认识。 看到话题少了，先等几秒再查一次，不要立刻怀疑代码。

3.2 这个话题两端是谁

ros2 topic info /robot1/imu/data

加上 --verbose（简写 -v）能看到每一端的节点名和完整 QoS：

ros2 topic info /robot1/imu/data --verbose

（节选）

Type: sensor_msgs/msg/Imu

Publisher count: 1

Node name: imu_talker
Node namespace: /robot1
Endpoint type: PUBLISHER
QoS profile:
  Reliability: BEST_EFFORT
  Durability: VOLATILE
  ...

Subscription count: 1

Node name: imu_listener
Node namespace: /robot1
Endpoint type: SUBSCRIPTION
QoS profile:
  Reliability: BEST_EFFORT
  Durability: VOLATILE

这条命令是排查「收不到消息」的核心工具：发布者和订阅者各有几个、分别是哪个节点、 两端的 QoS 是否一致，一次全看到。第四节会用它诊断故障。

3.3 看数据内容

ros2 topic echo /robot1/imu/data --once

--once 只打一条就退出，不加会一直刷。Imu 一条就有三十多行， 只想看某个字段时用 --field：

ros2 topic echo /robot1/imu/data --once --field linear_acceleration.z
9.81
---

嵌套字段用点号连接，和代码里写 msg.linear_acceleration.z 是同一套写法。

3.4 频率与带宽

ros2 topic hz /robot1/imu/data
average rate: 50.010
	min: 0.020s max: 0.020s std dev: 0.00014s window: 52

50 Hz，与参数 imu_hz: 50.0 一致。开头那行 WARNING: topic ... does not appear to be published yet 是正常的， 它只是说还没收到第一条，等一下就好。

ros2 topic bw /robot1/imu/data
16.53 KB/s from 49 messages
	Message size mean: 0.32 KB min: 0.32 KB max: 0.32 KB

一条 Imu 约 0.32 KB，50 Hz 就是每秒 16 KB。这个数字现在看着不大， 但换成 PointCloud2（激光点云）会是每秒几十 MB——带宽是选 QoS 和设计系统时的真实约束。

3.5 不写节点也能发消息

调试时经常需要「手动发一条试试」。ros2 topic pub 可以：

ros2 topic pub -r 2 /demo std_msgs/msg/String '{data: hello}'
publisher: beginning loop
publishing #1: std_msgs.msg.String(data='hello')

publishing #2: std_msgs.msg.String(data='hello')

-r 2 是每秒 2 次。消息内容用 YAML 写，字段名要和 interface show 里的一致。

--once 会先等至少一个订阅者。 没有任何节点订阅那个话题时，它会一直打印 Waiting for at least 1 matching subscription(s)... 然后什么也不发。 这不是卡住，是设计如此——它不想把消息发进虚空。 想单纯测试发布，先开一个 ros2 topic echo 订阅上。

3.6 反查与汇总

ros2 topic find sensor_msgs/msg/Imu

按类型反查话题，接入陌生机器人时很有用——不知道雷达发在哪个话题上， 按 sensor_msgs/msg/LaserScan 一查就知道。

ros2 node info /robot1/imu_listener

（节选）

/robot1/imu_listener
  Subscribers:
    /robot1/imu/data: sensor_msgs/msg/Imu
  Publishers:
    /robot1/imu/magnitude: std_msgs/msg/Float64

从节点的角度看：它订阅什么、发布什么。topic info 是从话题看两端， node info 是从节点看两侧，排查时两个换着用。

命令回答的问题
ros2 topic list -t系统里有哪些话题，各是什么类型
ros2 topic info <话题> -v这个话题两端是谁，QoS 是否匹配
ros2 topic echo <话题> --once数据长什么样，值对不对
ros2 topic hz <话题>发得快不快，稳不稳
ros2 topic bw <话题>占多少带宽
ros2 topic find <类型>哪个话题在发这种数据
ros2 topic pub <话题> <类型> '<yaml>'不写节点，手动发一条
ros2 node info <节点>这个节点订阅什么、发布什么

用上面任意四条命令描述一遍你正在运行的系统：几个节点、几条话题、 IMU 频率多少、带宽多少。说得出来，这一节就过了。

四、QoS：两个节点都在跑，却收不到

这是今天最重要的一节。

前两天只要话题名和类型对上就能通。传感器数据不一样——发布端和订阅端还必须在 「怎么传」上达成一致。这套约定叫 QoS（Quality of Service，服务质量）。

4.1 三个要素

要素取值含义
Reliability<br/>可靠性RELIABLE保证送到，丢了重传
BEST_EFFORT尽力而为，丢了就丢了
Durability<br/>持久性VOLATILE只发给当前在线的订阅者
TRANSIENT_LOCAL为晚到的订阅者保留最近的消息
History + Depth<br/>历史与队列深度KEEP_LAST + N只保留最近 N 条
KEEP_ALL全部保留（受底层限制）

代码里就是 Day 3 §1.2 那段：

qos = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    history=HistoryPolicy.KEEP_LAST,
    depth=10,
)

Day 1、Day 2 里 create_publisher(Int32, 'counter', 10) 的那个 10 其实就是简写：KEEP_LAST + depth=10 + 默认 RELIABLE。

4.2 为什么传感器用 BEST_EFFORT

50 Hz 的 IMU，每 20 毫秒一条新数据。如果某条丢了：

  • 用 RELIABLE：底层会重传，你在 100 毫秒后收到一条过期的数据， 而这期间已经有 5 条新数据了。重传的代价白付，拿到的还是旧值。
  • 用 BEST_EFFORT：直接丢掉，等下一条新的。

对连续采样的传感器，新数据总是比旧数据有用。 所以雷达、IMU、相机一律 BEST_EFFORT。反过来，地图、参数、指令这类「每一条都不能丢」的用 RELIABLE—— imu_listener 输出的 imu/magnitude 用的就是默认的 RELIABLE。

4.3 兼容规则

订阅端的要求不能高于发布端提供的。

发布端提供订阅端要求能通吗
RELIABLERELIABLE能
RELIABLEBEST_EFFORT能（要求更低，没问题）
BEST_EFFORTBEST_EFFORT能
BEST_EFFORTRELIABLE不能（发布端给不了这个保证）

Durability 同理：发布端 VOLATILE、订阅端要 TRANSIENT_LOCAL 也通不了。

4.4 亲手复现一次

ros2 topic echo 可以指定 QoS，不用改代码就能制造失配。保持系统运行， 在新终端里执行：

ros2 topic echo /robot1/imu/data --qos-reliability reliable --once
[WARN] [...]: New publisher discovered on topic '/robot1/imu/data', offering incompatible QoS. No messages will be received from it. Last incompatible policy: RELIABILITY

一条数据也收不到，但ROS2 明确告诉了你原因：不兼容的策略是 RELIABILITY。

换成兼容的一侧，立刻就有数据：

ros2 topic echo /robot1/imu/data --qos-reliability best_effort --once --field header.frame_id
imu_link
---

反方向也验证一下。imu/magnitude 是 RELIABLE 发布的，用 BEST_EFFORT 订阅—— 要求更低，应该能通：

ros2 topic echo /robot1/imu/magnitude --qos-reliability best_effort --once
data: 9.818498377788176
---

Durability 失配也是同样的表现：

ros2 topic echo /robot1/counter --qos-durability transient_local --once
[WARN] [...]: New publisher discovered on topic '/robot1/counter', offering incompatible QoS. No messages will be received from it. Last incompatible policy: DURABILITY

这条警告可能被淹没。 你自己写的节点如果 QoS 配错了，同样会打这条 WARN， 但它混在 launch 的一堆输出里很容易被划过去。 「话题名对、类型对、两边都在跑，就是没数据」时，第一件事是 ros2 topic info <话题> --verbose 对比两端的 QoS。

4.5 排查顺序

Day 1 给过三个条件，今天补全成完整的排查树：

flowchart TD
    A["收不到消息"] --> B{"ros2 topic list -t<br/>话题在吗，名字对吗"}
    B -- 不在 --> B1["发布端没跑，或 namespace 不对<br/>也可能只是发现还没完成，等几秒"]
    B -- 在 --> C{"类型一致吗"}
    C -- 不一致 --> C1["Int32 与 Int64 是两种类型<br/>改成一样的"]
    C -- 一致 --> D{"ros2 topic info -v<br/>两端 QoS 兼容吗"}
    D -- 不兼容 --> D1["看 WARN 里的 Last incompatible policy<br/>按 4.3 的表调整"]
    D -- 兼容 --> E{"Publisher/Subscription count<br/>都不为 0 吗"}
    E -- 有 0 --> E1["有一端根本没建起来<br/>回去看节点日志有没有报错"]
    E -- 都不为 0 --> F["数据应该是通的<br/>用 echo 确认，再查业务逻辑"]

能复现一次 QoS 失配，并用 topic info -v 指出是哪一端、哪个策略不兼容。

五、rosbag：把数据录下来

机器人调试有个现实问题：现象往往不可复现。雷达在某个角落丢了几帧、 IMU 在过减速带时出了个尖峰——你不可能每次都把机器人推到那个位置再看一遍。

ros2 bag 解决这个：把话题数据原样录下来，之后随时回放， 回放出来的话题和真机发出来的一模一样，所有订阅者都分辨不出区别。

5.1 录制

ros2 bag record -o ~/ros2_lab/imu_bag /robot1/imu/data /robot1/imu/magnitude

-o 指定输出目录名。后面跟要录的话题，可以写多个。 录几秒后按 Ctrl+C 停止。

[INFO] [rosbag2_recorder]: Subscribed to topic '/robot1/imu/data'
[INFO] [rosbag2_recorder]: Subscribed to topic '/robot1/imu/magnitude'
[INFO] [rosbag2_recorder]: All requested topics are subscribed. Stopping discovery...
[INFO] [rosbag2_cpp]: Writing remaining messages from cache to the bag. It may take a while
[INFO] [rosbag2_recorder]: Recording stopped

想录全部话题用 -a（--all）。但点云、图像这类话题体积极大， 录几分钟就是几个 GB，在真机上慎用 -a。

5.2 看看录到了什么

ros2 bag info ~/ros2_lab/imu_bag
Files:             imu_bag_0.db3
Bag size:          165.4 KiB
Storage id:        sqlite3
Duration:          6.400022535s
Messages:          642
Topic information: Topic: /robot1/imu/magnitude | Type: std_msgs/msg/Float64 | Count: 321 | Serialization Format: cdr
                   Topic: /robot1/imu/data | Type: sensor_msgs/msg/Imu | Count: 321 | Serialization Format: cdr

逐项读：

字段含义
Storage id: sqlite3存储后端。Humble 默认 sqlite3，数据就在那个 .db3 文件里
Duration录了多长时间
Messages总消息数
Count（每话题）各话题各录到多少条

拿这些数自查一遍：6.4 秒 × 50 Hz ≈ 320 条，实测 imu/data 321 条，对得上； imu/magnitude 也是 321 条，因为 imu_listener 每收到一条就发一条，两者一一对应。 数量对不上时说明中间有丢帧或处理跟不上，这是检查数据链路健康度最直接的办法。

目录里有两个文件：

ls ~/ros2_lab/imu_bag
imu_bag_0.db3
metadata.yaml

.db3 是数据，metadata.yaml 是索引（话题列表、类型、时间范围）。 两个都要保留，只拷贝 .db3 是放不了的。

5.3 回放

先把 launch 停掉（Ctrl+C），让系统里没有任何实时节点。然后：

ros2 bag play ~/ros2_lab/imu_bag

另开终端查看：

ros2 topic list
ros2 topic hz /robot1/imu/data
/robot1/imu/data
/robot1/imu/magnitude

average rate: 50.007
	min: 0.019s max: 0.021s std dev: 0.00031s window: 51

没有任何节点在跑，话题却回来了，频率也和录制时一致。 这就是 rosbag 的价值： 录一次现场，之后在办公室里反复调试算法，不用把机器人搬来搬去。

常用选项：

选项作用
--loop循环播放
-r 22 倍速
-r 0.5半速，看细节
--topics /robot1/imu/data只放其中一部分话题
-p启动后暂停，按空格开始

通过 SSH 跑 ros2 bag play 时会看到 stdin is not a terminal device. Keyboard handling disabled.—— 这只是说空格暂停之类的快捷键用不了，回放本身正常。

~/ros2_lab/imu_bag/ 下有 .db3 与 metadata.yaml， 停掉所有节点后 ros2 bag play 能让话题重新出现。

六、rviz2：把数据画出来

前面所有工具都是文字的。rviz2 是 ROS2 的三维可视化工具， 用来看点云、坐标系、机器人模型、路径。

rviz2

rviz2 需要图形界面。 通过 SSH 连到没有显示器的机器上直接运行会失败。 在本机的桌面环境里打开，或者配置 X11 转发。

今天数据只有 IMU 的数值，rviz2 里没什么可看的——它的主场在 Day 4： 小车模型、TF 坐标系、激光扫描线都要靠它确认。这里只需要记住三个必查项， 因为「rviz2 里看不到东西」是后面最常见的问题：

症状先查什么
加了 Display 但一片空白左上角 Fixed Frame 是否设成了一个真实存在的坐标系
点云/激光完全不出现Display 的 Reliability 是否设成了 Best Effort。传感器话题多是 BEST_EFFORT，rviz2 默认按 Reliable 订阅，就是第四节那个失配
数据闪一下就没消息的 header.stamp 是否正确。时间戳不对会被当成过期数据丢掉

三条全都是今天讲过的知识——坐标系、QoS、时间戳。

课后回顾

  1. imu_talker 用 BEST_EFFORT 发布，下面哪个订阅端收不到数据？

    1. BEST_EFFORT
    2. RELIABLE
    3. 两个都能收到
    4. 取决于 depth 的大小
    答案与解析

    B。订阅端要求不能高于发布端提供的；BEST_EFFORT 的发布端给不了 RELIABLE 的保证。见 §4.3。

  2. msg.header.frame_id 的作用是：

    1. 给每条消息编号，防止重复
    2. 声明这条数据是在哪个坐标系里测的
    3. 指定这条消息要发给哪个节点
    4. 记录消息的发送时间
    答案与解析

    B。frame_id 声明坐标系，stamp 才是时间。见 §2.1。

  3. ros2 topic pub --once /foo std_msgs/msg/String '{data: hi}' 一直打印 Waiting for at least 1 matching subscription(s)...，原因是：

    1. 话题名写错了
    2. 消息类型不存在
    3. 没有任何节点订阅 /foo，--once 会等到有订阅者才发
    4. QoS 不兼容
    答案与解析

    C。--once 会等至少一个订阅者才发布，避免把消息发进虚空。见 §3.5。

  4. 一条 Imu 消息里 orientation_covariance[0] 被设成 -1.0，表示：

    1. 姿态数据无效，这一项没有估计值
    2. 姿态的方差是负一
    3. 消息损坏
    4. 需要重新标定
    答案与解析

    A。这是 Imu 消息定义里写明的约定：没有估计值时把对应协方差的 第 0 个元素设为 -1。见 §2。

  5. 停掉所有节点后 ros2 bag play 回放，此时 ros2 topic hz 能测到 50 Hz。 这说明：

    1. 节点其实没停干净
    2. 回放进程本身就是一个发布者，对订阅者而言与真机无异
    3. hz 是从 bag 文件里直接读的
    4. 这是异常现象
    答案与解析

    B。回放进程是一个普通的发布者，订阅端分辨不出数据来自真机还是 bag。见 §5.3。

  6. rviz2 里添加了点云 Display 却一片空白，最先应该检查：

    1. 显卡驱动
    2. Fixed Frame 设的坐标系是否存在，以及 Display 的 Reliability 是否为 Best Effort
    3. 重装 rviz2
    4. 把点云话题改成 RELIABLE
    答案与解析

    B。这两条正是今天讲的坐标系与 QoS。见 §6。
