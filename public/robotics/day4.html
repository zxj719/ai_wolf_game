一、URDF：机器人的形状与关节

1.1 先看一眼要做出什么

一台差速小车，最少五个部件：车身、左右驱动轮、一个万向轮（防止前倾）、 一个雷达。IMU 没有形状，但也要占一个位置。

flowchart TD
    B["base_link<br/>车身 0.30 x 0.20 x 0.08"] -->|"left_wheel_joint<br/>continuous 绕 y 轴"| L["left_wheel"]
    B -->|"right_wheel_joint<br/>continuous 绕 y 轴"| R["right_wheel"]
    B -->|"caster_joint<br/>fixed"| C["caster_wheel"]
    B -->|"lidar_joint<br/>fixed"| D["lidar_link"]
    B -->|"imu_joint<br/>fixed"| I["imu_link"]

这张图就是 TF 树。Day 3 说过每条传感器数据都要带 frame_id—— 现在这些 frame_id 有了归属：lidar_link 就是雷达装的那个位置。

1.2 三个概念

link（连杆） 是一个刚体。三个可选子标签：

子标签作用不写会怎样
<visual>看起来什么样，rviz 和 Gazebo 用它显示看不见，但物理照常
<collision>碰撞用什么形状，物理引擎用它算接触穿模，车会沉进地面
<inertial>质量与转动惯量Gazebo 里模型行为异常，见第二节

visual 和 collision 常常写成一样的形状。真实项目里 visual 用精细网格、 collision 用简化的盒子或圆柱，因为碰撞检测比渲染贵得多。

joint（关节） 连接两个 link，说明它们的相对位置和能不能动：

类型含义本车用在哪
fixed焊死，不能动雷达、IMU、万向轮
continuous绕轴无限旋转两个驱动轮
revolute绕轴转，但有角度上下限本车没用到，机械臂常用
prismatic沿轴平移升降结构

origin 说明子 link 相对父 link 的位置和姿态：

<origin xyz="0 0.1125 -0.04" rpy="0 0 0"/>

xyz 是平移（米），rpy 是绕 x/y/z 轴的旋转（弧度，不是度）。 坐标系遵循 ROS 标准：x 向前，y 向左，z 向上。

rpy 用弧度。想转 90 度要写 1.5708 或在 xacro 里写 ${pi/2}， 写成 90 会转出去十几圈。

1.3 一个 link 长什么样

<link name="base_link">
  <visual>
    <geometry><box size="0.30 0.20 0.08"/></geometry>
    <material name="body_blue"><color rgba="0.2 0.4 0.8 1"/></material>
  </visual>
  <collision>
    <geometry><box size="0.30 0.20 0.08"/></geometry>
  </collision>
  <inertial>
    <mass value="3.0"/>
    <inertia ixx="0.0116" ixy="0" ixz="0" iyy="0.0241" iyz="0" izz="0.0325"/>
  </inertial>
</link>

那三个惯量数是算出来的，不是拍的——下一节讲。

二、inertial：质量与转动惯量

2.1 为什么必须填对

<mass> 好理解。<inertia> 是转动惯量矩阵，描述这个刚体绕各轴转动时有多"难转"。 它决定了车的加速、转向、遇到碰撞时的反应。

填错的后果不是报错，而是物理行为诡异：惯量填得过小，车会像纸片一样被轻微接触弹飞； 填得过大，电机推不动。这类问题在仿真里最难查，因为一切看起来都"正常运行"。

2.2 三个公式

矩阵是对称的，非对角项（ixy/ixz/iyz）在几何体规则且坐标轴与主轴对齐时都是 0。 本课程只用这三种：

几何体ixxiyyizz
长方体 边长 x, y, zm(y²+z²)/12m(x²+z²)/12m(x²+y²)/12
圆柱 半径 r, 长 l（绕 z 轴）m(3r²+l²)/12m(3r²+l²)/12mr²/2
实心球 半径 r2mr²/52mr²/52mr²/5

拿车身验算一遍：长方体 0.30 × 0.20 × 0.08，质量 3.0 kg。

ixx = 3.0 × (0.20² + 0.08²) / 12 = 3.0 × (0.04 + 0.0064) / 12 = 0.0116
iyy = 3.0 × (0.30² + 0.08²) / 12 = 3.0 × (0.09 + 0.0064) / 12 = 0.0241
izz = 3.0 × (0.30² + 0.20²) / 12 = 3.0 × (0.09 + 0.04)   / 12 = 0.0325

圆柱的 izz 和另外两个不一样。 izz 是绕自身轴（那根中心线）转， 只跟半径有关；ixx/iyy 是绕横着的轴翻滚，跟长度也有关。 Day 5 的考题里，轮子的惯量最容易在这里写错。

2.3 让 xacro 替你算

手算三个 link 六种数值容易错。xacro 支持表达式，把公式写进宏里，一次写对处处正确：

<xacro:macro name="box_inertia" params="m x y z">
  <inertial>
    <mass value="${m}"/>
    <inertia ixx="${m*(y*y+z*z)/12}" ixy="0" ixz="0"
             iyy="${m*(x*x+z*z)/12}" iyz="0"
             izz="${m*(x*x+y*y)/12}"/>
  </inertial>
</xacro:macro>

用的时候一行：

<xacro:box_inertia m="${base_m}" x="${base_x}" y="${base_y}" z="${base_z}"/>

圆柱和球同理。Day 5 允许你用宏，但要能说出公式的来历—— 考卷给公式不给数值，就是要你自己代入。

三、xacro：把重复消掉

纯 URDF 写两个轮子，除了名字和 y 坐标的正负号，其余完全一样。xacro 解决这个。

3.1 属性：给数值起名字

<xacro:property name="wheel_r"  value="0.05"/>
<xacro:property name="wheel_l"  value="0.025"/>
<xacro:property name="base_y"   value="0.20"/>
<xacro:property name="wheel_sep" value="${base_y + wheel_l}"/>

用 ${wheel_r} 引用。属性之间可以互相计算——wheel_sep（轮距）由车身宽度和 轮子厚度算出，改车身宽度时轮距自动跟着变，不会出现改了一处忘了另一处的错误。

3.2 宏：把一段结构参数化

<xacro:macro name="wheel" params="prefix reflect">
  <link name="${prefix}_wheel">
    <visual>
      <origin rpy="${pi/2} 0 0"/>
      <geometry><cylinder radius="${wheel_r}" length="${wheel_l}"/></geometry>
    </visual>
    ...
  </link>
  <joint name="${prefix}_wheel_joint" type="continuous">
    <parent link="base_link"/>
    <child link="${prefix}_wheel"/>
    <origin xyz="0 ${reflect * wheel_sep / 2} ${-base_z/2}"/>
    <axis xyz="0 1 0"/>
  </joint>
</xacro:macro>

<xacro:wheel prefix="left"  reflect="1"/>
<xacro:wheel prefix="right" reflect="-1"/>

reflect 传 1 和 -1，左右轮就分别落在 y 轴正负两侧。

圆柱默认沿 z 轴。轮子要绕 y 轴转，所以 visual 和 collision 里 都要加 <origin rpy="${pi/2} 0 0"/> 把它放倒。 忘了这步，车轮会是平躺的圆盘。

3.3 展开看看

xacro 不是运行时解释的，它先展开成纯 URDF：

cd ~/ros2_lab
xacro src/my_robot/urdf/my_robot.urdf.xacro > /tmp/my_robot.urdf
wc -l /tmp/my_robot.urdf
217 /tmp/my_robot.urdf

打开 /tmp/my_robot.urdf 看一眼，属性和宏都没了，只剩展开后的 link 与 joint。 调试 xacro 的第一步永远是先展开看结果，比盯着源文件猜快得多。

验证结构是否合法：

check_urdf /tmp/my_robot.urdf
robot name is: my_robot
---------- Successfully Parsed XML ---------------
root Link: base_link has 5 child(ren)
    child(1):  caster_wheel
    child(2):  imu_link
    child(3):  left_wheel
    child(4):  lidar_link
    child(5):  right_wheel

这就是第 1.1 节那张 TF 树，由工具确认过一遍。root Link 必须是 base_link 且只有一个——出现多个根说明有 link 没被 joint 连上。

四、robot_state_publisher：把 URDF 变成 TF

URDF 描述的是"各部件如何连接"。robot_state_publisher 负责把它翻译成实时的 TF：

flowchart LR
    A["URDF<br/>结构描述"] --> C["robot_state_publisher"]
    B["/joint_states<br/>各关节当前角度"] --> C
    C --> D["/tf<br/>会变的变换<br/>比如轮子转了多少"]
    C --> E["/tf_static<br/>不变的变换<br/>雷达装在哪"]
    C --> F["/robot_description<br/>把 URDF 原文发出来"]

fixed 关节进 /tf_static（只发一次，因为永远不变），可动关节进 /tf（持续更新）。

启动它：

ros2 run robot_state_publisher robot_state_publisher \
  --ros-args -p robot_description:="$(xacro src/my_robot/urdf/my_robot.urdf.xacro)"

（节选）

[INFO] [robot_state_publisher]: got segment base_link
[INFO] [robot_state_publisher]: got segment caster_wheel
[INFO] [robot_state_publisher]: got segment imu_link
[INFO] [robot_state_publisher]: got segment left_wheel
[INFO] [robot_state_publisher]: got segment lidar_link
[INFO] [robot_state_publisher]: got segment right_wheel

六个 link 都认出来了。

你还会看到一条警告： The root link base_link has an inertia specified in the URDF, but KDL does not support a root link with an inertia. 这条可以忽略。 它说的是 robot_state_publisher 内部用的 KDL 库不处理根节点的惯量—— 而惯量本来就是给物理引擎用的，Gazebo 会正常读取。

五、Gazebo 插件：让模型活起来

URDF 只描述了形状。要让轮子能被驱动、雷达能扫描，得挂插件。

<gazebo> 标签里的内容 URDF 本身不认识，是专门给 Gazebo 读的。

5.1 差速驱动

<gazebo>
  <plugin filename="ignition-gazebo-diff-drive-system"
          name="ignition::gazebo::systems::DiffDrive">
    <left_joint>left_wheel_joint</left_joint>
    <right_joint>right_wheel_joint</right_joint>
    <wheel_separation>0.225</wheel_separation>
    <wheel_radius>0.05</wheel_radius>
    <odom_publish_frequency>50</odom_publish_frequency>
    <topic>cmd_vel</topic>
    <odom_topic>odom</odom_topic>
    <frame_id>odom</frame_id>
    <child_frame_id>base_link</child_frame_id>
  </plugin>
</gazebo>

它订阅 cmd_vel（线速度 + 角速度），换算成两个轮子各自该转多快， 同时反过来根据轮子实际转了多少推算出车走到哪，发布 odom。

wheel_separation 和 wheel_radius 必须和 URDF 里的实际几何一致。 不一致不会报错，但车会走偏、转向角度不对——这是仿真里最难查的一类问题。 在 xacro 里用 ${wheel_sep} 和 ${wheel_r} 引用同一个属性，从根上避免。

5.2 激光雷达与 IMU

传感器挂在具体的 link 上，所以 <gazebo> 要带 reference：

<gazebo reference="lidar_link">
  <sensor name="lidar" type="gpu_lidar">
    <topic>scan</topic>
    <update_rate>10</update_rate>
    <always_on>true</always_on>
    <lidar>
      <scan><horizontal>
        <samples>360</samples>
        <min_angle>-3.14159</min_angle>
        <max_angle>3.14159</max_angle>
      </horizontal></scan>
      <range><min>0.12</min><max>10.0</max></range>
    </lidar>
    <gz_frame_id>lidar_link</gz_frame_id>
  </sensor>
</gazebo>

<gazebo reference="imu_link">
  <sensor name="imu" type="imu">
    <topic>imu</topic>
    <update_rate>100</update_rate>
    <always_on>true</always_on>
    <gz_frame_id>imu_link</gz_frame_id>
  </sensor>
</gazebo>

<gz_frame_id> 决定消息里的 header.frame_id——就是 Day 3 讲的那个字段。

5.3 世界文件里也要挂插件

传感器能不能出数据，还取决于世界加载了哪些系统插件：

<plugin filename="ignition-gazebo-sensors-system"
        name="ignition::gazebo::systems::Sensors">
  <render_engine>ogre2</render_engine>
</plugin>
<plugin filename="ignition-gazebo-imu-system"
        name="ignition::gazebo::systems::Imu"/>

缺 Sensors 插件，雷达一条数据都不会有，而且不报错。 缺 Imu 插件同理。查"传感器没数据"时，先看世界文件里这两个插件在不在。

gpu_lidar 顾名思义要用 GPU 渲染。没有图形环境时它出不了数据， 日志里会看到 libEGL warning: failed to create dri2 screen 之类的行。 在带显示器的机器上跑，或者配置离屏渲染。

六、ros_gz_bridge：仿真与 ROS2 之间的翻译

Gazebo 内部有自己的一套消息格式和传输机制，和 ROS2 不是一回事。 两边要通信，需要一个翻译。

flowchart LR
    subgraph GZ["Gazebo 内部"]
        S1["/scan<br/>ignition.msgs.LaserScan"]
        S2["/imu<br/>ignition.msgs.IMU"]
        S3["/odom<br/>ignition.msgs.Odometry"]
        S4["/cmd_vel<br/>ignition.msgs.Twist"]
    end
    B["ros_gz_bridge<br/>parameter_bridge"]
    subgraph ROS["ROS2"]
        R1["/scan<br/>sensor_msgs/msg/LaserScan"]
        R2["/imu<br/>sensor_msgs/msg/Imu"]
        R3["/odom<br/>nav_msgs/msg/Odometry"]
        R4["/cmd_vel<br/>geometry_msgs/msg/Twist"]
    end
    S1 --> B --> R1
    S2 --> B --> R2
    S3 --> B --> R3
    R4 --> B --> S4

注意 cmd_vel 的箭头是反的：指令从 ROS2 流向 Gazebo，传感器数据从 Gazebo 流向 ROS2。

配置写在 config/bridge.yaml：

- ros_topic_name: "cmd_vel"
  gz_topic_name: "cmd_vel"
  ros_type_name: "geometry_msgs/msg/Twist"
  gz_type_name: "ignition.msgs.Twist"
  direction: ROS_TO_GZ

- ros_topic_name: "scan"
  gz_topic_name: "scan"
  ros_type_name: "sensor_msgs/msg/LaserScan"
  gz_type_name: "ignition.msgs.LaserScan"
  direction: GZ_TO_ROS

direction 三种取值：ROS_TO_GZ、GZ_TO_ROS、BIDIRECTIONAL。 写反了不会报错，只是数据不流动。

启动：

ros2 run ros_gz_bridge parameter_bridge --ros-args \
  -p config_file:=src/my_robot/config/bridge.yaml
[INFO] [ros_gz_bridge]: Creating ROS->GZ Bridge: [cmd_vel (geometry_msgs/msg/Twist) -> cmd_vel (ignition.msgs.Twist)] (Lazy 0)
[INFO] [ros_gz_bridge]: Creating GZ->ROS Bridge: [odom (ignition.msgs.Odometry) -> odom (nav_msgs/msg/Odometry)] (Lazy 0)
[INFO] [ros_gz_bridge]: Creating GZ->ROS Bridge: [scan (ignition.msgs.LaserScan) -> scan (sensor_msgs/msg/LaserScan)] (Lazy 0)
[INFO] [ros_gz_bridge]: Creating GZ->ROS Bridge: [imu (ignition.msgs.IMU) -> imu (sensor_msgs/msg/Imu)] (Lazy 0)

每一条桥都要在这里出现。 少一条就是 YAML 写错了，回去核对类型名拼写。

/clock 是 Gazebo 发的仿真时间。逐个确认有数据：

ros2 topic echo /scan --once

（节选）

  frame_id: lidar_link
angle_min: -3.141590118408203
angle_max: 3.141590118408203
range_min: 0.11999999731779099
range_max: 10.0

确认话题有没有数据，用 ros2 topic echo --once 比 ros2 topic hz 可靠。 实测同一套系统里 hz 会对 /imu、/odom 报 does not appear to be published yet，而 echo --once 立刻就能拿到数据。 hz 需要在它的统计窗口内持续收到消息才给结果。

雷达是不是真扫到东西了？世界里在 (0, -2) 放了一个 0.4 米宽的箱子， 车在原点朝 +x，那个箱子应该出现在正右方（−90°）约 1.8 米处：

样本数 360  有限值 39 个
最近 1.800 m  最远 2.125 m
首个命中: 索引84 角度-95.8° 距离1.809m

360 个方向里只有 39 个测到东西，其余是 inf（该方向 10 米内没有障碍）。 最近 1.800 m——箱子中心 2 米，减去半个箱子 0.2 米，对得上。

      y: -7.928327190682717e-20
      z: 0.0

0.3 × 5 = 1.5 米，实测 1.49 米。差的那一厘米来自启动和停止时的加速过程。 这个数对得上，说明 URDF 的轮子半径、轮距与插件配置三者是一致的—— 对不上就回去查 5.1 节那个警告。

课后回顾

  1. 圆柱形轮子的 izz 与 ixx 不同，原因是：

    1. 计算公式抄错了
    2. izz 是绕自身轴转，只跟半径有关；ixx 是横着翻滚，跟长度也有关
    3. 轮子不是标准圆柱
    4. izz 必须比 ixx 大
    答案与解析

    B。见 §2.2 的注记。这也是 Day 5 最容易写错的一处。

  2. check_urdf 报告出现两个 root link，最可能的原因是：

    1. 有两个 base_link
    2. 某个 link 没有被任何 joint 连接到树上
    3. 质量填成了 0
    4. xacro 展开失败
    答案与解析

    B。TF 树必须是单根，孤立的 link 会形成第二个根。见 §3.3。

  3. 车在仿真里被轻轻碰一下就飞出去，最先该查：

    1. 显卡驱动
    2. <inertial> 里的质量与惯量是否过小
    3. 世界文件的光照
    4. bridge 的 direction
    答案与解析

    B。惯量过小时任何接触力都会产生巨大角加速度。见 §2.1。

  4. /scan 在 Gazebo 侧有数据，ROS2 侧没有，最先查：

    1. 雷达的 update_rate
    2. bridge.yaml 里这条的类型名与 direction
    3. URDF 的 lidar_joint
    4. 车的位置
    答案与解析

    B。Gazebo 侧有数据说明传感器正常，问题在翻译这一层。见 §6。

  5. 世界文件里漏掉 Sensors 插件的表现是：

    1. Gazebo 启动失败并报错
    2. 雷达完全没有数据，但不报任何错
    3. 模型不显示
    4. 车无法移动
    答案与解析

    B。缺插件不报错，只是静默无数据——所以要养成先查插件的习惯。见 §5.3。

  6. 发 /cmd_vel 让车以 0.3 m/s 走 5 秒，/odom 却显示走了 3 米。最可能的原因：

    1. 仿真时间不准
    2. 插件里的 wheel_radius 比 URDF 里实际轮子大一倍
    3. IMU 没标定
    4. odom_publish_frequency 设太低
    答案与解析

    B。里程计是按轮子转数 × 半径推算的，半径参数错一倍，推算距离就错一倍。见 §5.1。
